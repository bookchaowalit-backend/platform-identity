## 1. ปัญหา

ปัจจุบัน identity, การตัดสินสิทธิ์, workflow, graph, tasks และ monitor
อยู่รวมกันใน repo `platform-empire` และใช้ Postgres database เดียวกัน:

| ส่วน | อยู่ที่ไหนตอนนี้ |
|---|---|
| identities, workspaces, memberships, roles, role_permissions, membership_roles, policies, delegations | schema `platform` (migration 0001–0002) |
| authorization decision point: `platform.authorize`, `authorization_decisions` | schema `platform` (0003) |
| executions, approvals, cell_executions, `begin/finish_execution` | schema `platform` (0003, 0005–0007) |
| audit_events, `record_audit` (append-only) | schema `platform` |
| ออก token | CLI ใน local machine (`empire-dev-token`, `empire-automations provision`, `empire-token-rotate`) เซ็นด้วย RSA key บนเครื่อง owner, issuer `empire-platform` |
| ตรวจ token | ทุก cell pin public key PEM ไว้ใน env (`<ENV>_JWT_PUBLIC_KEY_PEM`, `<ENV>_JWT_ISSUER`) |
| token exchange | `token_exchange.py` เป็น prototype ใน process ยังไม่มี endpoint |
| owner login | life-dashboard-web ใช้ Google OAuth + allowlist subject; metadata APIs เชื่อ service JWT ของ web + owner allowlist; remote MCP ใช้ Clerk OAuth + allowlist |

ผลคือ:

1. **ไม่มี tenant ที่สอง:** ทุก token ถูก mint ด้วยมือบนเครื่องเดียว
   จึงเปิดให้ลูกค้าหรือ workspace ใหม่สมัครเองไม่ได้
2. **หมุน key ยาก:** การหมุน signing key ต้องแก้ env ของทุก cell พร้อมกัน
3. **login หลายแบบ:** มี 3 วิธี login และมี allowlist ซ้ำกันหลายที่
4. **contract เก่า:** `contract.json` ของ repo นี้ยังชี้ไปที่ `infra/api/*.ts`
   ใน hub ซึ่งไม่ใช่ implementation ปัจจุบันแล้ว
   (implementation จริงอยู่ใน `platform-empire`)

## 2. เป้าหมายและสิ่งที่ไม่ทำ

**เป้าหมาย**
- `platform-identity` เป็น service เดียวที่ตอบคำถาม 3 ข้อ:
  "ใครคือคนนี้", "อยู่ workspace ไหน" และ "ทำ action นี้ได้ไหม"
- รองรับหลาย tenant: สร้าง workspace, เชิญสมาชิก, ให้ role และออก API key
  ได้เองผ่าน API โดยไม่ต้องใช้เครื่อง owner
- cell ตรวจ token ผ่าน JWKS แทนการ pin PEM จึงหมุน key ได้โดยไม่ต้อง redeploy cell
- ย้ายโดยไม่มี downtime และ rollback ได้ทุกขั้น

**สิ่งที่ไม่ทำ (non-goals)**
- ไม่ทำ password หรือ MFA เอง ให้ provider ภายนอกเป็นคนยืนยันตัวคน (ดู D3)
- ไม่ย้าย workflow, graph หรือ tasks ในเอกสารนี้ เอกสารนี้แค่กำหนดขอบเขตให้
- ไม่เปลี่ยนรูปแบบ permission string `<domain>.<resource>:<action>`

## 3. ขอบเขตของ service

```
                 human login (OIDC provider, D3)
                          │ id_token
                          ▼
  ┌──────────────── platform-identity ────────────────┐
  │ identities · workspaces · memberships · roles     │
  │ role_permissions · policies · delegations         │
  │ api_keys · signing_keys · authorization_decisions │
  │ audit_events (identity + authz)                   │
  │                                                   │
  │ /.well-known/jwks.json   /v1/token (exchange)     │
  │ /v1/authz/decide         /v1/workspaces…          │
  └───────────────────────────────────────────────────┘
        ▲ JWKS (cache)          ▲ decide
        │                       │
  cells (life-*, finance-*, platform-*-api) · MCP · web
        │ begin/finish execution
        ▼
  platform-workflow-api (executions · approvals · cell_executions)
```

| เป็นของ platform-identity | ย้ายไปที่อื่น (ขั้นถัดไป) |
|---|---|
| identities, workspaces, memberships | executions, approvals, cell_executions → `platform-workflow-api` |
| roles, role_permissions, membership_roles, policies, delegations | graph events/consents → `platform-graph-api` |
| `authorize` + `authorization_decisions` | tasks → `life-tasks-api` |
| api_keys (ใหม่), signing_keys (ใหม่) | monitor → `platform-observability` |
| audit ของ identity/authz | audit ของ domain อยู่กับเจ้าของข้อมูลแต่ละตัว |

**ทำไม policies กับ delegations อยู่กับ identity:** ทั้งสองอย่างเป็นข้อมูลที่ใช้
ตัดสินสิทธิ์ ถ้าแยกออกไป ทุกครั้งที่ decide จะต้องเรียกข้าม service
ส่วน **approvals** อยู่กับ workflow เพราะมันคือสถานะของงานแต่ละชิ้น
ไม่ใช่สิทธิ์

## 4. Data model

ตารางใน schema `platform` ปัจจุบันย้ายมาเป็น schema `identity` ทั้งชุด
ไม่เปลี่ยนคอลัมน์ ส่วนที่เพิ่มใหม่:

```sql
-- API key: เก็บแค่ hash (argon2id/sha256+pepper) และแสดงตัวจริงครั้งเดียวตอนสร้าง
CREATE TABLE identity.api_keys (
    id           uuid PRIMARY KEY DEFAULT identity.uuid_v7(),
    workspace_id uuid NOT NULL REFERENCES identity.workspaces (id),
    identity_id  uuid NOT NULL,              -- service_account หรือ automation
    prefix       text NOT NULL UNIQUE,       -- 8 ตัวอักษรแรก ไว้ค้นและแสดงใน UI
    key_hash     text NOT NULL,
    scopes       identity.permission[] NOT NULL CHECK (cardinality(scopes) > 0),
    expires_at   timestamptz,
    revoked_at   timestamptz,
    last_used_at timestamptz,
    created_at   timestamptz NOT NULL DEFAULT now(),
    FOREIGN KEY (workspace_id, identity_id) REFERENCES identity.memberships (workspace_id, identity_id)
);

-- Signing key: เก็บแค่ public key; private key อยู่ใน secret store ของ runtime
CREATE TABLE identity.signing_keys (
    kid         text PRIMARY KEY,
    alg         text NOT NULL CHECK (alg IN ('RS256', 'EdDSA')),
    public_jwk  jsonb NOT NULL,
    status      text NOT NULL CHECK (status IN ('next', 'active', 'retiring', 'retired')),
    activated_at timestamptz,
    retired_at   timestamptz
);
```

ส่วนที่เพิ่มในตารางเดิม:
- `workspaces.plan` (`free|pro|…`, default `free`) สำหรับ SaaS tier
  ไม่ใส่ข้อมูล billing ในนี้
- `identities.external_issuer` คู่กับ `external_subject` เพื่อให้รับ login
  จากหลาย provider ได้ unique ใหม่คือ `(external_issuer, external_subject)`

RLS ใช้ pattern เดิมต่อ: `FORCE ROW LEVEL SECURITY` + `app.workspace_id`
service ตั้งค่า workspace ใน transaction ทุกครั้ง และ role ของ service
ไม่มี `BYPASSRLS`

## 5. Token

| Token | ออกโดย | อายุ | ใช้ทำอะไร |
|---|---|---|---|
| access token (JWT) | `/v1/token` | 5–15 นาที | เรียก cell หรือ MCP |
| API key (opaque, `emp_<prefix>_<secret>`) | `/v1/workspaces/{id}/api-keys` | ตั้งได้ ไม่เกิน 1 ปี | automation หรือ integration แลกเป็น access token |
| provider id_token | OIDC provider | ตาม provider | แลกเป็น access token ครั้งแรก |

**Claims** คงชุดเดิมเพื่อให้ cell ไม่ต้องแก้ ได้แก่ `iss`, `aud`, `sub`, `ws`,
`iat`, `exp` และ `jti` ส่วน `delegation` ใส่ก็ต่อเมื่อมี
- เพิ่ม `kid` ใน header
- ช่วง transition คง `iss=empire-platform` ไว้ หลัง cutover ค่อยเปลี่ยนเป็น URL
  ของ identity

**`/v1/token`** ทำตามรูปแบบ RFC 8693 token exchange เหมือน `token_exchange.py`
ที่มีอยู่ subject ที่รับได้มี 3 แบบ:
- provider id_token
- API key
- access token ที่มี audience `empire-mcp` (กรณี MCP แลก token ลงไปเรียก cell)

**การหมุน signing key** ใช้ 4 สถานะ `next → active → retiring → retired`
JWKS แสดงทั้ง `next`, `active` และ `retiring` ทุก 30 วัน:
1. สร้าง key `next`
2. รออย่างน้อย 1 ชั่วโมงให้ cache ของ cell อัปเดต
3. สลับ `next` เป็น `active`
4. เก็บ key เดิมไว้เป็น `retiring` นานเท่าอายุ token สูงสุด แล้วจึง `retired`

ระหว่างทาง cell ไม่ต้อง redeploy

**การตรวจ token ฝั่ง cell (cellkit):**
- ใช้ `<ENV>_JWT_JWKS_URL` ถ้ามีค่า ถ้าไม่มีให้ fallback ไปใช้ PEM เดิม
- cache JWKS 10 นาที
- ถ้าเจอ `kid` ที่ไม่รู้จัก ให้ refetch ได้ไม่เกิน 1 ครั้งต่อนาที

## 6. API (v1)

| Method | Path | Permission |
|---|---|---|
| GET | `/.well-known/jwks.json` | public |
| GET | `/.well-known/openid-configuration` (เฉพาะ fields ที่ใช้) | public |
| POST | `/v1/token` | subject token ที่ถูกต้อง |
| POST | `/v1/authz/decide` | service token (ย้ายมาจาก platform-empire โดยใช้ body/response เดิม) |
| POST/GET | `/v1/workspaces`, `/v1/workspaces/{id}` | `identity.workspace:admin` |
| POST/DELETE | `/v1/workspaces/{id}/members` | `identity.membership:admin` |
| PUT | `/v1/workspaces/{id}/members/{identity}/roles` | `identity.role:admin` |
| POST/DELETE | `/v1/workspaces/{id}/api-keys` | `identity.api-key:admin` |
| POST/DELETE | `/v1/workspaces/{id}/delegations` | `identity.delegation:write` |
| GET | `/v1/me` | access token |

ทุก write ต้องส่ง `Idempotency-Key` และเขียน audit ใน transaction เดียวกัน
error ใช้รูปแบบ problem+json

## 7. ลำดับการย้าย (strangler, ไม่มี downtime)

ทุกขั้นมีเกณฑ์ผ่าน (gate) และวิธี rollback

| ขั้น | ทำอะไร | Gate | Rollback |
|---|---|---|---|
| 0 | แก้ `contract.json` ของ repo นี้ให้ชี้ `platform-empire` เป็น current implementation และใส่ interface จริง (decide, token, JWKS) | `scripts/check.sh` ผ่าน | revert commit |
| 1 | ใน `platform-empire` เพิ่ม `/.well-known/jwks.json` จาก public key ที่ใช้อยู่ และเพิ่ม JWKS fallback ใน cellkit | cell ทุกตัว verify ผ่าน JWKS ได้ใน staging | ลบ env `JWKS_URL` แล้ว cell กลับไปใช้ PEM |
| 2 | ตั้ง `<ENV>_JWT_JWKS_URL` ให้ cell ทีละตัว | health + smoke ของแต่ละ cell เขียว 24 ชม. | ลบ env ตัวนั้น |
| 3 | สร้าง service `platform-identity` (Python/FastAPI แบบเดียวกับ cell) ใช้ DB เดิม schema `platform` ผ่าน role ใหม่ที่ grant เฉพาะตาราง identity และเปิด `/v1/token` กับ `/v1/authz/decide` แบบ shadow | shadow decide ตรงกับของเดิม 100% ใน 7 วัน (log diff ไม่มี payload) | ปิด service |
| 4 | ให้ `EMPIRE_PLATFORM_URL` ของ cell ชี้ decide ไป identity ทีละตัว (endpoint execution ยังอยู่ที่เดิม) | error rate ไม่เพิ่ม, p95 decide < 50 ms | สลับ URL กลับ |
| 5 | ย้าย automations ให้แลก API key → access token แทน mint บนเครื่อง และปิด cron `empire-token-rotate` | automation ทุกตัวรันผ่าน 1 รอบ | เปิด cron เดิม (key เดิมยังใช้ได้) |
| 6 | รวม login: life-dashboard-web, metadata APIs และ remote MCP แลก provider token ที่ `/v1/token` แทน allowlist | owner login ได้ทุกช่องทาง | feature flag กลับไปใช้ allowlist |
| 7 | แยก DB: สร้าง Neon project ของ identity, logical replication schema identity → ตรวจ row count/checksum → สลับ write (read-only สั้น ๆ < 1 นาที) | parity ผ่าน | สลับกลับ DB เดิม (replication ย้อนทาง) |
| 8 | ลบตาราง identity ออกจาก DB ของ platform-empire หลังผ่าน 30 วัน | ไม่มี query ถึงตารางเดิม | snapshot ก่อนลบ |

**เรื่อง FK ข้าม DB:** หลังขั้น 7 ตาราง `executions` และ `cell_executions` จะอ้าง
`identity_id` และ `workspace_id` แบบ FK ไม่ได้แล้ว ให้เก็บเป็นค่า uuid ธรรมดา
แล้วตรวจที่ decide แทน (decide ผ่านก่อนเขียนทุกครั้ง) ส่วน RLS ยังใช้
`app.workspace_id` เหมือนเดิม

## 9. ความปลอดภัย

- private signing key ไม่อยู่ใน DB หรือ repo ให้อยู่ใน secret store ของ runtime
  ระยะยาวควรย้ายไปใช้ KMS
- API key เก็บแค่ hash และแสดงค่าจริงครั้งเดียว log เก็บแค่ prefix
- rate limit ที่ `/v1/token` แยกตาม IP และตาม API key prefix
- audit ทุกครั้งที่ grant หรือ revoke role, key หรือ delegation
  audit เป็น append-only เหมือน `reject_audit_change` ที่มีอยู่
- repo นี้เป็น public ห้ามมี key, subject จริง, email หรือข้อมูล workspace
